## 摘要

本文档描述一套**生产级、真实资金运行、持续自进化**的 AI Agent 系统架构。系统以三大量化交易子系统（K1/S1/T1）为业务载体，构建了"采集 → 分析 → 决策 → 执行 → 复盘 → 进化"的完整闭环，实现从静态规则系统到数据驱动自进化系统的升级。

核心贡献：
1. **三维市场监督层（Meta-Supervisor）**：市场阶段 × 资金炒作节奏 × 情绪周期 → 多系统协同指导
2. **决策记忆闭环（Decision Memory Loop）**：平仓反思 → 历史注入 → 仓位自适应
3. **自进化执行层（Self-Evolving Executor）**：生态扫描 → 分类决策（小优化自动/大优化人工）
4. **生产级可观测与自愈体系**：cron 健康检查、数据源监控、进程自愈

## 2. 三大业务系统（载体）

### 2.1 系统定位

| 系统 | 周期 | 池 | 策略 | 杠杆 | 退出链 |
|:----|:----|:---|:----|:----|:------|
| **K1** | 15m | 19 固定主流币 | v4.2 加法信号（IC优化） | 按波动分组 5-15x | 硬止损→ATR止损→三档止盈→趋势反转 |
| **S1** | 5m | 动态山寨池（≥1500万U） | 情绪周期+评分+7出口 | 多3x/空2x | 结构止损→超时→硬止损→反转→箱体→三档→移动→乖离 |
| **T1** | 15m | 139 美股/ETF永续 | TradFi 趋势跟随+Kelly | 动态 | 追踪止盈+超时+部分止盈 |

### 2.2 加密货币市场特性（架构前提）

- 节奏快 + 无涨跌幅限制 + 24h 不停市
- **日周期太慢，4h 是最小合理复盘周期**（赚钱效应识别/入池判定用 4h）
- 周度仓位控制为唯一保留的"日级"例外（用户明确要求）

## 3. 三维市场监督层（Meta-Supervisor）

### 3.1 设计目标

站在市场阶段、资金炒作节奏、情绪周期三个维度，为 K1/S1/T1 提供方向、仓位、频率、时间/空间维度的统一指导。

### 3.2 架构

```
phase_current.json ──┐
                     ├→ market_supervisor.py → directive.json → supervisor_client → 三系统
capital_flow ────────┤        (每15min cron)     (K1/S1/T1指导)
sentiment ───────────┘
```

### 3.3 三维输入

| 维度 | 数据源 | 档位 |
|:----|:------|:----|
| 市场阶段 | `phase_current.json` | launch/main_up/bottom_building(强) / top_building/retreat(弱) |
| 资金节奏 | mainstream_flow + sector_heat + 链上 | inflow / neutral / outflow |
| 情绪周期 | market_sentiment | safe / cautious_safe / caution / danger |

### 3.4 输出指令（directive.json）

```json
{
  "dimensions": {
    "phase": {"stage": "top_building", "strength": 1.0, "leader": "LINK", "sector": "预言机"},
    "capital": {"flow": "neutral", "confidence": 0.42},
    "sentiment": {"action": "cautious_safe"}
  },
  "systems": {
    "K1": {"direction": "short_priority", "pos_scale": 0.56, "freq_scale": 0.6,
            "time_dim": "冲顶做空优先", "space_dim": "高位减仓"}
  }
}
```

### 3.5 镜像方向设计（用户核心哲学）

| 市场阶段 | 做多 | 做空 |
|:--------|:----|:----|
| launch/main_up/bottom_building（强） | 顺势正常仓 | **逆势微仓 (0.1-0.2)** |
| top_building/retreat（弱） | 逆势微仓 | **顺势正常仓 (0.6-1.0)** |
| 极强多头逼空 | — | **跳过开空** |

### 3.6 自适应调优（v1.1，数据驱动进化）

基于决策记忆的近期胜率动态微调：
- 系统胜率 <40% → 仓位 ×0.85（表现差收紧）
- 系统胜率 ≥70% 且样本≥5 → 仓位 ×1.1（表现好放宽）
- 连亏 ≥3 笔 → 频率 ×0.7

**实例**：S1 近期表现差，监督层自动将其频率从 ×1.0 降至 ×0.7——无需人工干预。

## 4. 决策记忆闭环（Decision Memory Loop）

### 4.1 设计来源

借鉴 TradingAgents（95K★）的 decision-log → reflection → injection 设计，落地为轻量规则引擎（无 LLM 依赖，可审计）。

### 4.2 三层架构

```
① 记录 record_close()  → decision_memory.jsonl (平仓时)
② 反思 _reflect()      → 按退出原因自动归因 (入场失败/趋势正确/追高失败/震荡粘滞)
③ 注入 get_symbol_adjustment() → 下次开仓前查询同标的近期表现 → 调整仓位
```

### 4.3 注入规则

| 条件 | 动作 | 验证 |
|:----|:----|:----|
| 同标的近10笔胜率<40%（≥3笔） | 降仓 ×0.7 | XRP 4笔1胜 → ×0.7 ✅ |
| 同标的连亏≥2 | 降仓 ×0.7 | SOL 连亏2笔 → ×0.7 ✅ |
| 同标的胜率≥70% 且 ≥3笔 | 加仓 ×1.15 | BTC 3连胜 → ×1.15 ✅ |
| 无记录/样本不足 | ×1.0 | 空记忆 → ×1.0 ✅ |

### 4.4 数据校验（v1.2，防污染）

- pnl_pct 超 ±200% 丢弃（entry_price=0 兜底污染防护）
- entry ≤0 丢弃
- 已清理 3 条历史脏数据（-416万% 异常值）

### 4.5 参数自适应（v1.3）

`get_adaptive_params()` 基于历史盈亏分布自动推荐：
- 平均亏损 > 止损×1.5 → 止损放宽（防频繁扫损）
- 平均亏损 < 止损×0.5 → 止损收窄（防扛单）
- 胜率低+盈亏比差 → 降仓；胜率≥65%+盈亏比佳 → 加仓

## 5. 赚钱效应复盘（Profit Effect Analysis）

### 5.1 核心问题（用户驱动）

1. 最近哪些标的有赚钱效应？
2. 三大系统是否做到了？
3. 做到了是否吃到大头利润？没做到怎么优化？

### 5.2 4h 周期识别（v1.0 关键决策）

- 加密市场节奏快 → **用 4h 涨幅替代 24h 涨幅**
- `market_4h.py`：对比 6 根 4h K线前收盘价计算涨幅
- 4h 涨幅≥3% + 成交量过滤 → 赚钱效应榜

### 5.3 分析输出

| 维度 | 内容 |
|:----|:----|
| 覆盖率 | 各系统做到的标的数 / 涨幅榜总数 |
| 利润捕获率 | (系统已获涨幅 / 市场涨幅) × 100% |
| 归因 | 漏掉的原因：固定池限制 / 现货无合约 / 信号未触发 / 时机问题 |

### 5.4 真实发现案例

- **ZEC 虚假亏损**：分析器用今日价对比7月入场价 → 时间错配误报，已加 24h 过滤
- **S1 覆盖率失真**：420 条开仓记录全部价格=$0.00（save_state bug）→ 修复后真实覆盖率为 0%，暴露 S1 实盘链路问题

## 6. 自进化执行层（Self-Evolving Executor）

### 6.1 每日生态扫描（cron 08:00 CST）

```
self_evolve_collect.py (GitHub/HN采集)
  → 分析层 (LLM): 分类汇总
  → 小优化: 自动实施 (脚本/skills/配置微调)
  → 大优化: 列清单待用户决策 (框架升级/模型切换)
  → Notion 推送 + QQ 报告
```

### 6.2 决策机制

| 类别 | 判定 | 处理 |
|:----|:----|:----|
| 小优化 | 脚本 bug、配置微调、skill 补丁 | 自动执行 + 记录在日报 |
| 大优化 | Hermes 升级、模型切换、框架级改动 | 只列建议（理由/风险/工作量），用户拍板 |

### 6.3 真实案例

- 自动发现 Codex release 拉取失败（IncompleteRead）→ 自动 per_page 10→2 修复
- 自动识别 Hermes v0.19.1 升级建议 → 列清单待用户决策

## 7. 生产级可观测与自愈

### 7.1 四层健康体系

| 层 | 组件 | 频率 | 机制 |
|:--|:----|:----|:----|
| 进程自愈 | `self_heal.py` | 30s | DataHub/TCM/Cloudflared/Sing-box 崩溃重启 |
| Cron 健康 | `cron_health_check.py` | 6h | 连续失败≥3告警 / ≥5建议暂停 |
| 数据源监控 | `data_source_health.py` | 5min | 主源延迟+失败率，异常切备用 |
| 市场监控 | `smart_monitor.py` | 15min | BTC/PnL/告警/资源四维扫描 |

### 7.2 降级安全设计

所有监督注入点 `try/except` 包裹 + 函数内局部导入：
- directive 缺失 → 自动回退 ×1.0 正常仓位
- 数据源异常 → 不阻塞主流程
- **任何组件故障绝不影响实盘下单**

## 9. 设计哲学

1. **规则 + Agent 混合**：确定性系统（量化硬约束）与概率系统（LLM 分析）融合——不是纯 LLM 循环
2. **量价只做验证不做预测**：监督层是规则引擎，可审计、无幻觉
3. **先保本再增值**：所有自进化以风险可控为前提（降级安全、人工决策大优化）
4. **数据驱动进化**：静态规则 → 决策记忆 → 胜率自适应，逐步升级
5. **务实增量**：先核心后完善，够好就行
